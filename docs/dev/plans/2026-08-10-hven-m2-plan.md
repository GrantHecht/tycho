# hven M2 — Implementation Plan (tycho-authored)

**Status:** ACTIVE (Grant's go, 2026-08-10). Per the standing staffing
agreement this plan is tycho-authored with **no SQP review required** —
M2 touches only the IPM engine, in which the SQP side holds no equity.
Companion documents: rev B (`tycho_sqp/docs/notes/2026-08-08-unified-
nlp-library-integration-plan-revB.md`, §Sequencing M2 + rule 4), the
frozen M1 spec (`2026-08-08-hven-m1-linear-and-rig-spec.md`, with its
post-freeze amendments), the consumed-surface audit
(`hven/docs/consumed-surface-audit.md`), and the M1 exit package.

**Goal:** the IPM engine (ex-PSIOPT) migrates from `tycho/psiopt/` into
the hven repo — renamed to `hven::`, retargeted onto `hven::linear` —
and tycho consumes hven by sibling path, passing its entire gate suite
bit-identically.

## The gate (rev B, verbatim scope)

Golden rig old-vs-new (P+T series, incl. the Mac leg) **plus** tycho

## Global constraints

- **Bit-identity is sacred (rev B sequencing rule 4).** M2 migrates
  psiopt AS-IS: file content moves byte-identical except (a) the
  namespace rename `tycho::` → `hven::`, (b) include-path updates, and
  (c) the Task-4 linear retarget. Placement into hven's mechanism dirs
  is a PATH-ONLY restructure. TU-rationalization (splits/merges) runs
  ONLY after the gate is green, as its own task, under the ratified
  verification standard (compile-flags diff, counter/corpus
  bit-identity, bench window; build benefit gated on parallel
  wall-clock + peak RSS).
- **The knobs directive (Grant, 2026-08-09):** all relevant backend
  knobs become NAMED options with don't-write-by-default semantics (at
  the default, hven does not touch the backend parameter; the backend's
  init value survives exactly). No raw iparm passthrough — that stays
  dropped. Per-backend semantics rows are mandatory wherever one field
  name covers different backend meanings. The MKL-iparm human-review
  gate for the M2 knob set is satisfied by that ruling.
- **Governance carries unchanged:** notices/ immutability (Pardiso- and
  Accelerate-derived files keep their dual-heritage notices as they
  move); never-fabricate-Apple-values; SNOPT firewall (no SQP-side
  content moves in M2); no internal labels in shipped code.
- **tycho's `psiopt/` subtree stays in the tree, frozen and un-built,
  until M6 removes it.** M2 flips the root build to sibling-path hven;
  the standalone-psiopt smoke check retires from the pre-merge sequence
  at that flip (its "separately buildable" guarantee transfers to
  hven's own CI).
- **The rig's `sqp-old` arm and every SQP-side pin are untouched.** The
  `psiopt-old` seam stays pinned at 060ad213 — it is the "old" half of
  the old-vs-new gate.
- Error rules T5/T6 and the B.2 thread-pin comparison policy continue
  to bind all new code and every rig table.

## Task breakdown

Ordering: Task 1 → Task 2 → Task 3 → Task 4 → Task 5 → Task 6 →

### Task 1 — option-set + evidence expansion in `hven::linear`
**[hven repo — Anthropic implementer until the Codex workspace root
lands]**

Implements the B.5(d) dispositions under the knobs directive, BEFORE
any engine code moves — the migrated engine cannot reproduce its proven
configuration until the surface can express it:

- Named options (all don't-write-by-default on MKL): matrix scaling
  (`iparm[10]`), pivot strategy (`iparm[20]`), factorization algorithm
  (`iparm[23]`), parallel solve mode (`iparm[24]`), and CNR
  reproducibility (`iparm[33]`, finding 4 — written only when enabled,
  from the option's thread count). Accelerate: documented no-analogue
  treatment per option (the weighted_matching precedent — throw or
  best-effort-absent, decided per knob by what the backend can honor;
  the choice is part of the task, reviewed against the audit).
- Accelerate zero tolerance as its own named option and its own gate
  row (finding 8).
- Evidence: factor size and factor flops join `SolveInfo` (finding 5)
  with the MANDATORY per-backend semantics row — MKL's `iparm[17]`
  (nonzero count) and Accelerate's byte count never share an
  undifferentiated field name.
- Construction-validation tests per `docs/testing.md`'s existing
  option-test conventions (both presets; the Apple half rides the
  syntax lane + macOS CI); rig re-derivation only for rows the new
  options touch (expected: none — defaults don't write).

Exact option names are the implementer's proposal, locked at task
review. Gate: hven three-OS CI green.

### Task 4 — the linear retarget
**[hven repo — the delicate one; Opus-tier implementer]**

Per the Task 2 design note: the engine's KKT solve path drops
`pardiso_interface`/`accelerate_interface` and consumes
`SymmetricFactor` (analyze/factorize/solve lifecycle, solve_partial for
the 331/332/333 phases, InertiaEvidence for the inertia reads, SolveInfo
for mem/flops). The old classes are deleted. The engine's own inertia
logic keeps its exact current behavior — the adapter presents the same
values it saw before; honesty-surface adoption inside the engine is M4+
territory, not M2. Gate: hven suite green + golden rig old-vs-new on
Linux — every P/T row the migrated engine produces matches the pinned
`psiopt-old` arm's committed rows exactly (the docketed deltas are
linear-layer rows already owned by the native arm, enumerated in the
design note so the comparison has zero unexplained differences).

**Amendment (Ipopt adapter).** hven's own surface carries no interface to a
foreign solver, so the Ipopt TNLP adapter, its no-Ipopt stub, the backend
selector, and the build option behind them are removed from hven rather than
migrated. They re-land on tycho's side of the boundary in Task 5, wired under
tycho's existing `ENABLE_IPOPT`. Tycho carries foreign-solver interfaces; hven
does not.

### Task 5 — tycho flips to sibling-path hven
**[tycho repo — Codex-eligible]**

Root build consumes `../hven` (configurable dir, sibling-path default;
`add_subdirectory(psiopt)` removed), `src/solvers/`
(OptimizationProblem), `solvers_vf/`, and the bindings retarget to hven
headers and `hven::` names. `psiopt/` stays in-tree, un-built.
CLAUDE.md and the pre-merge sequence update (standalone smoke retired,
hven documented as a build prerequisite). Gate: tycho
builds + fast smoke (unit tests) against hven.

**Amendment (how hven is consumed).** Not a sibling path: hven is a git
submodule of tycho at `dep/hven`, added to the root build as a CMake
subdirectory. `TYCHO_HVEN_DIR` (default `dep/hven`) still lets a developer
point the build at an external checkout. This task also re-lands the Ipopt
adapter per the Task 4 amendment above.

**Amendment (two C++ renames at the flip).** The backend-aware problem base is
`tycho::solvers::BackendProblemBase`; `OptimizationProblemBase` now means the
solver library's backend-less class and is deliberately unreachable through
tycho's solver namespace, as is `NLPSolver` — backend selection lives only on
the OptimizationProblem layer, so the solver-neutral NLP interface is spelled
`hven::solvers::NLPSolver`. Both old spellings fail to compile rather than
rebinding. The Python surface is unchanged.

### Task 5.5 — the function-entry seam, and GenericFunction comes home
**[both repos — one commit each]**

The Task 5 flip left hven naming its consumer's central type: the solver
interfaces forward-declared `hven::vf::GenericFunction` and took it by
reference in a preferred constructor, which forced tycho to define
`GenericFunction` inside `namespace hven::vf` and import it back into
`tycho::vf`. That inverts the dependency, and the generic constructor beside
it accepted any other dense VectorFunction silently, erasing it a second time
for a second virtual dispatch per solver call with no diagnostic. The seam
replaces both constructors with a customization point,
`hven::solvers::SolverInterfaceAdapter<T>`, that a type's owner specializes
beside the type's definition: concrete families register for direct storage,
`GenericFunction` registers to hand its wrapped function over, and an
unregistered type is a compile error with an authored message rather than a
quiet dispatch. The hven commit landed first (it stays green on its own);
this tycho commit bumps the submodule, adds the adapters and the per-family
registrations, and moves `GenericFunction` back into `tycho::vf`. The contract
a consumer has to satisfy — where a registration lives, and what an erased
handle must expose to keep single-dispatch storage — is written out in
`dep/hven/include/hven/solver_interface_adapter.h`, which is also the one
header a consumer includes to opt in.

### Task 5.6 — hven install/export rules
**[hven repo]**

Upcoming. hven currently builds as a CMake subdirectory of tycho and nothing
else, so its install and export rules are untested: there is no verified
`install()` set, no exported target namespace a consumer outside this tree
could link against, and no packaged public-header set. The task defines them
and proves them from a consumer project that finds hven with `find_package`
rather than `add_subdirectory`. It is the last structural piece of hven
standing on its own, and it is deliberately after the seam — the public
header surface an install rule has to name is exactly what the seam just
settled.
