## Global constraints

- Library name **hven** (locked); namespace `hven::`, headers
  `include/hven/…`, target `hven::hven`.
- Licenses: Apache-2.0; notices migrate per rev B §3; `notices/` is
  never modified after migration except to add new dependencies.
- Governance carries (rev B §9) go into the repo's founding CLAUDE.md,
  verbatim — including the MKL iparm human-review flag, the
  never-fabricate-Apple-values rule, and the SNOPT firewall.
- Eigen/fmt submodule pins = tycho's exact current SHAs.
- Error rules T5/T6 (validate at boundaries; no exit(); throw with
  formatted message) bind all new code.
- Comparison policy B.2 (thread-pinned assertions) binds every rig
  table.
- No PSIOPT/solver-internals behavior change rides along in M1: the
  fabrication fixes (P4/P5 semantics) land in `hven::linear`'s NEW
  implementation only; tycho's in-tree psiopt is untouched until M2.
- **TU structure [RULED, Grant 2026-08-08]:** hven makes appropriate use
  of separate TUs to optimize builds — not header-only, and less
  header-heavy than psiopt is today — but never at noticeable runtime
  cost. For M1 this binds directly: `linear/` and the dense factor are
  concrete, non-template classes and are implemented in `src/` .cpp TUs
  from day one (public headers carry declarations only). The
  library-wide operationalization (hot-path/orchestration split,
  verification standard, M2 sequencing) is recorded in the rev B
  addendum.

## Task breakdown

Ordering: Task 1 → Task 2 → (Task 3 ∥ Task 4) → Task 5 → Task 6 →
Task 7 → Task 8; Task 8.5 (three-OS CI) runs any time after Task 2 once
the GitHub remote exists, and must be green before M1 exit. The freeze
review (Task 0) can run concurrently with Tasks 1–2, which it does not
gate. (Plan tasks are "Task N" throughout —
the bare "T1–T8"/"P1–P6" names always mean rig TRACES, never tasks.)

### Task 0 — SQP freeze review of Part A/Part B [gate for Task 5+]
STATUS: COMPLETE — Part B [FROZEN as amended]; Part A [FROZEN as
amended] per the review addendum (epoch-based co-owning handles;
partial-solve surface + phase-33x rule + supports_partial_solve
predicate; A.5 new-law migration note; T2b + T4b traces). Post-freeze
changes ride the freeze gate.

### Task 1 — repo creation and skeleton [tycho territory]
Create the `hven` repo (fresh, per rev B §3): directory skeleton
(`include/hven/{core,linear,model,kkt,interior,qp,globalization,
warmstart,drivers}/` + `detail/` mirrors, `src/`, `tests/`, `bench/`,
`bindings/`, `cmake/`, `dep/`, `notices/`, `docs/`), Apache-2.0 LICENSE,
`.clang-format` (tycho's, verbatim), `.gitignore`, README stub, and the
founding **CLAUDE.md** carrying: the governance section (rev B §9
verbatim), the build rules, the counters-are-currency and pin
disciplines, and the process-hardening list. Add `dep/eigen`, `dep/fmt`
submodules at tycho's pinned SHAs. Migrate `FindMKL.cmake` /
`FindAccelerateSparse.cmake` and the shared compile-options module from
the psiopt subproject (the psiopt-split precedent: same flags, same
`SYSTEM INTERFACE` treatment of vendored deps).

### Task 2 — root CMake + CI lanes [tycho territory]
`project(hven LANGUAGES CXX)`, C++20; options `HVEN_BUILD_TESTS` (ON),
`HVEN_BUILD_BENCH` (OFF), `HVEN_BUILD_BINDINGS` (OFF); backend detection
(MKL on Linux/Windows, Accelerate on Apple) with a hard, clear error
when absent; `hven` interface/library target exporting include dirs +
backend links; GTest via FetchContent for tests. CI: one Linux MKL lane
(configure, build, ctest); the Mac lane is documented as the manual
hardware routine (MACBENCH-style) until a runner exists — the lane doc
lives in `docs/` and the M2/M3 gates reference it. Verification per the
standing rule: the lane must build AND run end-to-end before the task
closes (configure-success is not validation).

### Task 3 — `core/` seed [tycho territory]
Only what `linear/` and the rig need now (YAGNI): `hven::Index` and
scalar typedefs; the pattern-hash utility (FNV-1a over index arrays —
the library-wide structural key, one implementation, used by `linear/`
now and the model contract at M4); the counters-contract doc page
skeleton in `docs/`. Threading utils, settings shapes, and ledger
migrate at M2/M3 with their engines — not now.

### Task 4 — `DenseSymmetricFactor` + LAPACKE shim migration [tycho territory]
Small and self-contained (spec A.4): migrate the Accelerate LAPACKE shim
from tycho_sqp (with provenance header per the headers-say-Tycho rule
adapted to hven), implement the dense factor/solve over LAPACKE (MKL) /
shim (Apple), unit tests with analytic small matrices. Lands before Task 5
so the sparse work can test interleaving (T2-trace shape) early.

### Task 5 — `SymmetricFactor` on MKL Pardiso [frozen spec A.3/A.5/A.6]
The core implementation: lifecycle (analyze/factorize/solve), pattern-
hash keying, `InertiaEvidence` (derived-zero marking, perturbed-pivot
counter), counters, thread pinning via `mkl_set_num_threads_local`,
handle handoff + adopt (spec A.3). Implementation raids psiopt's
`pardiso_interface.h` (Eigen-derived — MPL notice preserved) for the
proven Pardiso call discipline, restructured behind the new surface.
Unit tests: lifecycle counters, misuse-throws, inertia on
known-inertia fixtures, handoff/adopt semantics, multi-RHS,
refinement-iters presence.

### Task 6 — `SymmetricFactor` on Accelerate [frozen spec A.5]
The Accelerate implementation incl. the two fabrication fixes as NEW
semantics: `perturbed_pivots = nullopt` (absent, never zero) and
`SparseGetInertia` failure → `kQueryFailed` (never zero-filled).
Compile-verified on Linux (the Apple-TU compile lane trick from the
psiopt split); functional verification happens on the Mac leg in Task 8.
Per the never-fabricate rule: no expected value for Apple behavior is
written down in this task — tables stay `UNOBSERVED` until Task 8.

### Task 7 — golden rig: harness + adapters + traces [frozen spec B.1–B.4]
The `SeamUnderTest` concept, the three adapters, the T1–T8 + T2b +
T4b / P1–P6 trace implementations from both rig halves, the expected-table format with
provenance banner + thread-pin column (traces T1–T8 + T2b + T4b from the SQP half,
P1–P6 from the tycho half), `hven_golden_rig_report`, and
the consumed-surface audit tooling (B.4). The audit runs here and its
report feeds the Task-0-frozen option set — if it surfaces consumed surface
outside the frozen spec, that is a spec change and goes back through
the freeze gate (small, fast, but never silent).

### Task 8.5 — three-OS PR CI workflows [tycho territory; RULED addition]
Grant's directive (2026-08-08): hven gets GitHub PR workflows testing on
**Linux, macOS, and Windows**. Supersedes the Linux-only-plus-manual-Mac
CI scope. Deliverables:
- `.github/workflows/ci.yml` extended to a three-job matrix:
  - **Linux** (ubuntu-latest): clang + Ninja + Intel oneAPI MKL (apt,
    cached), release preset, build + ctest — the existing lane.
  - **macOS** (macos-latest, Apple Silicon): AppleClang/LLVM + Ninja,
    Accelerate (ships with the OS), a `macos-release` preset added HERE
    (where it can actually be run — the earlier don't-write-unrunnable-
    preset rule is satisfied by the runner), build + ctest. NOTE: these
    runners are real Apple hardware — Accelerate test results here are
    OBSERVED, not fabricated; this upgrades the Mac verification story.
    Rig pin TABLES still derive on a named stable machine, but
    absence/state assertions (perturbation-field ABSENT, kQueryFailed)
    run and count as hardware legs in CI.
  - **Windows** (windows-latest): clang-cl (LLVM preinstalled on the
    runner; matches the LLVM-always rule), Ninja, Intel oneAPI MKL
    (installer or nuget, CACHED — the install is large), a
    `windows-clang-release` preset, build + ctest.
- Trigger: `pull_request` + `push` to main; concurrency-cancel stale runs.
- All three jobs required-green before merge (branch protection is a
  GitHub-settings step for Grant, noted in docs/ci.md).
- `docs/ci.md` rewritten: three PR lanes + the pin-derivation machine
  policy (CI legs verify; pin tables still name their derivation machine).
- DEPENDENCY: a GitHub remote must exist first. Creating it is Grant's
  call (outward-facing) — the task blocks on that and on nothing else;
  workflow YAML can be written and lint-checked before the remote exists.
- Verification: the standard rule — the lanes must RUN green on GitHub
  (a scratch PR) before the task closes; YAML-lint alone is not
  validation. Windows/macOS preset configure+build must be proven on the
  runners (that IS their end-to-end run).

### Task 8 — derivation + gates [spec B.3/B.5]
Execute B.3: old-seam derivation runs (MKL, pinned threads), expected
tables written, P4/P5 docket entries filed, full suite green on
`hven::linear`, one Mac hardware leg (Grant's machine) filling every
Mac slot. M1 exit = B.5 checklist complete + Task 2's CI lane green +
standalone `cmake -S hven && ctest` green from a clean clone
(submodules recursive).

## M1 exit criteria (roll-up)

1. Fresh-clone standalone build + full test suite green (Linux MKL).
2. Golden rig: all traces green on `hven::linear` both backends; Mac
   slots filled; P4/P5 dockets filed against the old seam.
3. Consumed-surface audit committed; frozen spec reconciled against it.
4. Three-OS PR CI (Linux, macOS, Windows) green on GitHub; pin-
   derivation machine policy documented; CLAUDE.md governance section in
   place.
5. No tycho or tycho_sqp source modified (M1 touches only the new repo;
   old-seam adapters compile against read-only checkouts).

## What M1 explicitly does not do

No engine migration (M2/M3). No model contract (M4). No WarmStart/
crossover (M5). No tycho submodule flip (M6). No bindings (M7). No
behavior change to tycho's shipped psiopt — the fabrication fixes exist
only in `hven::linear` until M2 retargets onto it.
